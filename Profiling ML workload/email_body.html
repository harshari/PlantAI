Profiling ML workload · DAG-to-hardware-mapping method

From a HuggingFace model card to a probabilistic hardware-mapping DAG — two worked examples

This is a walkthrough of a method for turning any HuggingFace model into a kernel-level, probabilistic workload DAG — the input format our floorplan / chiplet-placement search needs. The method is general, not tuned to one model: two contrasting worked examples follow, plus the four-step recipe both of them follow, so you can run this on a model of your own choosing.

One correction up front, because it's easy to get wrong: a DAG is not “one DAG per probability.” A workload's DAG template (its nodes and edges) can have zero, one, or many independent stochastic decision points — and even multiple instances of what looks like “the same layer type” inside one model can differ in whether they're stochastic at all (see DeepSeek's hash-routed vs. learned-routed MoE layers below). Sweeping the parameter of one distribution gives you multiple operating points of the same template, not multiple templates.

The general method, in four steps

1. Pull static architecture inputs from config.json — hidden size, layer count, attention/KV heads, FFN width, activation function, attention pattern, vocab size, precision. All deterministic, same every forward pass.

2. Decompose each repeating block into kernels — a mechanical recipe once step 1 is known: norm → qkv_proj[matmul] → attention → out_proj[matmul] → norm → ffn[matmul(s)+activation] → ffn_down[matmul]. Each kernel gets an op type, a FLOPs formula, and a bytes formula.

3. Separate communication into three kinds — weight bytes (read from local HBM, dominates at low batch), local I/O bytes (on-chip activation/KV), and inter-node bytes (the only kind that crosses the interconnect and feeds a NoC simulator). Conflating these is the classic mistake.

4. Find the stochastic decision points — NOT in config.json. This comes from the inference algorithm, and needs either a published closed form or actual profiling.

Example 1 — Muse Glimmer-30B (speculative decoding)

What it is: a dense causal transformer with an attached perception encoder, 27.8B parameters, all activated every forward pass. 52 layers, hidden size 6,656, GQA attention (32Q/2KV) with a repeating [local,local,local,global] pattern — 39 layers use a 2,048-token sliding window, 13 use full-context attention. Ships a small 5-layer draft model (32Q/8KV) for speculative decoding, proposing 16-token blocks.

Why it's probabilistic: the draft model guesses up to 16 tokens, the full model verifies in parallel and accepts a prefix. Tokens accepted per block, k, follows P(k=j) = αj(1−α), where α is the per-token acceptance probability — the entire stochastic surface of this workload. Every DAG edge fires with probability 1; only the payload size is random.

Kernel-level correction: task B (draft) isn't one parallel pass over 16 positions — it's 16 sequential micro-steps, since the draft model can't know token 2 before generating token 1. Matters for placement: B's steps are serially dependent (limited pipelining value), while C's 52 layers over 16 positions run in true parallel.

What the analysis found: at short context (L=1,500), task A is compute-bound (its FFN matmul dominates); B and C are bandwidth-bound (streaming a full weight matrix for one token is the classic batch=1 memory-bound case). At long context (L=100,000), A's dominant kernel itself flips from FFN-compute to attention-bandwidth — reading back the growing KV cache becomes the bigger transfer than any weight matrix.

Example 2 — DeepSeek-V4-Flash (MoE + hybrid attention + speculative decoding)

What it is: a Mixture-of-Experts model, 284B total parameters, only 13B activated per token — that gap is the tell for MoE vs. Glimmer's dense 27.8B where everything fires every time. 43 layers, hidden size 4,096. Every layer: 1 shared expert (always fires) + 256 routed experts (6 chosen per token). Supports 1M-token context via a hybrid attention scheme. Ships a multi-token-prediction module inference engines attach as a speculative-decoding drafter (branded “DSpark”), proposing 7-token blocks.

Why it's probabilistic — two independent layers, a different kind of randomness than example 1:

  (a) Expert routing — “which 6 of 256 experts” is a genuine categorical distribution, a real structural branch (which edge fires), not just a payload-size scalar like α. This is exactly the traffic-equation machinery from the original toy example, which Glimmer's workload never needed.

  (b) But not every MoE layer is stochastic. The first 3 layers use Hash routing — a deterministic function of token ID, a lookup, zero probability involved. Only the other 40 layers use learned, data-dependent routing that needs a profiled histogram to characterize. Two instances of “the same layer type” differing in whether they're random at all.

Two structural surprises this model forced into the kernel vocabulary: its hybrid attention is a 6-kernel pipeline (compress → index (FP4) → top-k select → attend → grouped output projection), not Glimmer's one fused attention op. And its residual-connection replacement (mHC) is 20 sequential Sinkhorn-Knopp steps on a tiny 4×4 matrix — utterly negligible in FLOPs/bytes, but bound by sequential dependency depth, a resource axis neither compute-bound nor bandwidth-bound roofline math covers. Needed a new op type: iterative_normalize.

Diagram: sent to you separately as deepseek_dag_figure.png — note the contrast between MOE.router_learned (red, reduce_argmax, stochastic) and MOE.router_hash (green, lookup, deterministic): same layer type, different mechanism. MHC.sinkhorn_iterate (purple) is the new op type.

From DAG to BookSim: injection rate, anynet, traces

Injection rate isn't chosen — it's measured. BookSim's injection_rate field is for synthetic traffic (uniform random, tornado) where every node injects at one fixed rate. Our traffic is heterogeneous and DAG-driven, so we use trace-driven mode instead: every packet's injection cycle comes from simulating the DAG. The effective rate is then measured afterward (in our worked example: 6.6×10−9 packets/cycle/node — sparse, as expected) for comparison against a synthetic sweep.

Anynet is BookSim's arbitrary-topology mechanism — needed because our placement is irregular (A and C deliberately share physical chiplets, since they run identical 52-layer weights). Traces come from a real discrete-event simulation: walk the DAG, sum each task's kernel latencies at the request's actual context length, layer a per-chiplet queue on top so concurrent requests actually contend, convert to cycles, write one packet per line.

Takeaways for your own model

• Config.json gives you the deterministic half for free; the stochastic half is never in the config — it's a property of the inference algorithm.
• Count the independent stochastic decision points before coding: zero (a vision encoder), one (Glimmer's α), or several at once (DeepSeek's routing + MTP).
• Don't assume every instance of a layer type shares the same probabilistic behavior — DeepSeek's hash-routed vs. learned-routed MoE layers are the cleanest counterexample.
• When a kernel's FLOPs and bytes both look negligible, check whether it's a sequential dependency chain instead (mHC) — a resource axis roofline math doesn't cover.
